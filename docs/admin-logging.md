# Admin log viewer

Production Rails logs go to container stdout. `config/logging` provides a single-host Grafana, Loki, and Alloy setup for collecting containers named `spellhub-web-*`. Grafana requires a separate login. The Rails admin Logs page links to it via `ADMIN_LOGS_URL`; it does not proxy logs or credentials.

Before deployment, provision server storage and backups for the three Docker volumes, verify disk capacity for 30 days of logs, and arrange monitoring and restore tests. Loki and Alloy are internal to the Compose network; Loki has no authentication of its own. Grafana binds only to localhost. Expose it through an authenticated HTTPS reverse proxy or private network and restrict access to administrators. Docker socket access grants substantial host privileges: protect the Alloy container and its configuration. Log output can contain sensitive information; restrict access and avoid debug logging.

On the logging host, set `GRAFANA_ADMIN_USER`, `GRAFANA_ADMIN_PASSWORD`, and `GRAFANA_ROOT_URL` through a protected deployment secret mechanism. Run `docker compose -f config/logging/compose.yml up -d` from the repository root. Create individual Grafana accounts with appropriate permissions, then set `ADMIN_LOGS_URL` in the Rails deployment's `env.clear` in `config/deploy.yml` to the HTTPS Grafana Explore URL and redeploy. Search the Loki datasource for `{job="spellhub"}` and filter by error text or request ID; adjacent lines provide request context. Generate a controlled test error and verify it appears. If the container naming differs, adjust the Alloy discovery filter.

This is a single-host starting point, not a high-availability production architecture. Grafana recommends Helm or Tanka for production Loki installations; select a supported architecture and TLS/authentication for the deployment environment before exposing it. Back up Grafana configuration and users as well as Loki data, and test restoring them. Pin and update images through the normal security maintenance process.
